1大作业要求拆解（先读懂规则）

动手前，先把「老师到底怎么打分」吃透。这门课的考核是三块，60% 的分数都在"各阶段完成度"上，而"完成度"本质是——你在华为云 DevCloud 上把每个环节操作了一遍并留下了痕迹。

核心结论 11 个环节里，只有「开发提交」需要真正写代码，其余 10 个都是 DevCloud 平台操作。所以策略是：代码够用就行，把 80% 的精力花在"把 DevCloud 每个环节走通 + 截图留痕 + 写总结"上。每个环节做完立刻截图，这些截图是报告（25%）和答辩的硬素材。

2实现路线：自研 vs 二次开发

你手上已经有一个现成的开源博客 OneBlog（DBlog）。作业原文明确写「软件源码可由同学们自行开发，亦可利用网上相应的开源资源进行二次开发」，所以两条路都合规。先对比，再给你推荐。

2.1 方案对比

维度方案 A：二次开发 OneBlog方案 B：自研精简版
前期投入低（登录/文章/评论/后台全现成）高（登录鉴权、CRUD、前端全自己写）
原创度 / 答辩可讲性中（需做"看得见的改造"）高（每一行都是自己的）
功能与演示效果强（RBAC、SEO、评论审核等齐全）弱（功能精简、界面朴素）
技术栈SpringBoot 2.3.5 + JDK8 + Shiro + Freemarker + Bootstrap3（偏老）可自选 SpringBoot 3.x + Thymeleaf（新）
环境复杂度需 MySQL + Redis（稍多）仅 MySQL（简单）
对 DevCloud 契合度高（Maven 多模块 + Docker，正好练构建/部署）高
2 人 9 周风险低中高（编码易挤占 DevCloud 与报告时间）

2.2 我的推荐：方案 C（A 为主 + 自研特色功能）

推荐路线 以 二次开发 OneBlog 打底（省下 3~4 周编码时间），同时自研 1~2 个"特色功能"作为原创亮点，例如：暗黑模式切换、标签云/归档页、访客统计、文章点赞、Markdown 目录等。这样既把时间花在 60% 的 DevCloud 流程上，答辩时又有"我们自己写的代码"可讲。
二次开发的两条红线（务必遵守）
  • 改造要"看得见"：改站点名/Logo/配色/首页布局，并至少新增 1 个自研功能，否则会被认为"照搬"。每次改造单独开一个功能分支提交，形成可讲的提交历史。
  • 诚实标注来源：在 README 和总结报告里明确写"基于 OneBlog（Gitee: yadong.zhang/DBlog，GPL v3）二次开发"，这是 25% 总结 + 15% 思考里非常好的素材（开源协议、二次开发的工程决策）。

注：OneBlog 是 GPL v3 协议，二次开发后若对外发布需同样开源；课程作业内部提交不涉及，但报告里提到这点会显得专业。

3一般软件开发流程（敏捷DevOps）

一个软件项目从 0 到交付，业界标准流程是一个 DevOps 无限循环：规划 → 编码 → 构建 → 测试 → 发布 → 部署 → 运维 → 监控，再回到规划。落到本作业，就是下面这条线，每一步我都标了对应的 DevCloud 拿分点。

① 需求分析 ──▶ ② 项目规划 ──▶ ③ 架构设计 ──▶ ④ 编码实现 ──▶ ⑤ 代码检查
     (需求文档)     (拆Story/迭代)   (选型/建库)    (功能分支提交)   (质量门禁)
        │                                                               │
        └──⑨ 总结复盘 ◀── ⑧ 运维监控 ◀── ⑦ 持续交付 ◀── ⑥ 编译构建+CI ◀┘
          (总结25%+思考15%)  (分支管理)   (流水线)      (构建配置+持续集成)
#阶段核心产出DevCloud 拿分点
1需求分析需求文档、用户故事（Story）项目管理-规划（5%）
2项目规划Story 拆解、优先级、迭代计划工作项（5%）+ 迭代（5%）
3架构设计技术选型、数据库设计、模块划分—（写进报告）
4编码实现可运行代码（登录/文章/评论）代码托管-开发提交（5%）
5代码检查质量报告代码检查（5%）
6编译构建构建成功 + 发布包构建配置（6%）+ 持续集成（5%）
7部署系统上线可访问主机配置（6%）+ 部署配置（8%）
8分支与持续交付稳定的 Master + 流水线分支合并（5%）+ 流水线（5%）
9总结复盘总结报告 + 思考建议总结描述（25%）+ 思考建议（15%）
为什么这个顺序 它体现的是「敏捷迭代 + DevOps 自动化」：需求拆成小 Story，放进短迭代（每 1~2 周）交付；代码提交后自动构建、自动部署，形成"提交即上线"的流水线。你的总结报告（25%）要讲的正是这条链路的方法论和你的实践体会。

4.1 两人分工（角色 A / 角色 B）

角色建议人选负责方向关键产出
角色 A（队长/DevOps）A秦庆泽项目管理（规划/工作项/迭代）、后端改造、编译构建、持续集成、部署、流水线、分支管理DevCloud 全流程配置与截图、后端代码、部署文档
角色 B（开发/文档）B队友需求文档、数据库设计、前端页面改造、代码检查、功能测试、总结报告与思考建议需求/设计文档、前端、测试报告、总结报告（25%+15%）
分工原则 角色 A 主攻「DevCloud 那条 60% 的线」，角色 B 主攻「文档和 40% 的总结线」。但两件事要交叉配合：DevCloud 每个环节两人一起过一遍（都能讲），总结报告必须两人一起写（引用双方截图）。每周开一次 15 分钟站会同步进度与卡点。

5各阶段保姆级操作指南

下面是每个阶段的目标 → 步骤 → 两人分工 → 验收标准 → 交付物。照着做即可，每个阶段末尾都指向第 6 章的对应 AI 提示词。

阶段 1 · 需求分析与项目规划W1 · 10-26~11-01A 主导，B 配合

目标：产出需求文档，并在 DevCloud 上完成「规划 → 工作项 → 迭代」三个拿分环节（合计 15%）。

具体步骤

  1. 用第 6 章的提示词 P1 让 AI 生成一份需求文档（用户故事格式），覆盖：登录、发表文章、编辑/删除文章、评论、文章列表/分类/标签、后台管理、我的特色功能。
  2. 登录华为云 DevCloud，新建项目（Scrum 模式），命名「个人博客」。
  3. 进入「规划」→ 用思维导图把需求拆成 Story 层级（Epic「博客系统」→ Feature「用户模块/文章模块/评论模块」→ Story「用户登录」「发布文章」…）。
  4. 保存后 Story 会自动进入「工作项」，逐条补全字段：描述、优先级（P0/P1/P2）、开始/结束日期、预计工时、重要程度。
  5. 进入「迭代」，创建迭代 1、迭代 2，把 Story 按「优先级高→低」拖入对应迭代。
  6. 每完成一步截图（思维导图、工作项列表、迭代看板）。

验收标准（完成度检查）

  • 思维导图里 Story 层级 ≥ 3 层，Story 总数 ≥ 10 个。
  • 每个 Story 的优先级/日期/工时字段已填写。
  • 至少 2 个迭代，Story 已按优先级分配。

交付物：需求文档（.md / .docx）+ DevCloud 截图若干。

AI 提示词 → P1

阶段 2 · 架构设计与环境搭建W2 · 11-02~11-08B 主导，A 配合

目标：确定技术选型与数据库设计，把 OneBlog 代码接入 DevCloud 代码仓库，本地/云端能跑。

具体步骤

  1. 用提示词 P2 生成「系统架构说明 + 数据库 ER 图/建表 SQL」，作为设计文档。
  2. 安装本地环境：JDK 8、Maven、MySQL、Redis（OneBlog 依赖）。或直接用 DevCloud 的 CloudIDE 云端开发（免装本地）。
  3. 在 DevCloud 新建代码仓库，把 OneBlog 代码 git init → 添加远端 → git push 推上去（或用 CloudIDE 直接导入）。
  4. 初始化数据库：导入 docs/docker/mysql/dblog.sql 与 init_data.sql。
  5. 跑通前后台：启动 BlogWebApplication 和 BlogAdminApplication，浏览器能访问首页和后台（root/123456）。

验收标准

  • 设计文档含架构图（文字/图）与完整建表 SQL。
  • 代码已在 DevCloud 仓库，提交历史可见。
  • 本地/云端能访问博客首页与后台登录页。

交付物：架构设计文档 + 数据库脚本 + 仓库首次提交。

AI 提示词 → P2

阶段 3 · 迭代1：核心功能开发W3 · 11-09~11-15A 后端 / B 前端

目标：确认登录、发表文章、评论三大功能可用，完成首次代码提交与代码检查（10%）。

具体步骤

  1. 在功能分支 feature/xxx 上做二次开发（改名、改 Logo、按需微调功能）。禁止直接在 Master 上改。

  4. 在 DevCloud 运行代码检查服务，选 Java 规则集，跑一遍并截图。

AI 提示词 → P3、P4

阶段 4 · 迭代2：改造与特色功能W4 · 11-16~11-22B 主导特色功能，A 协助

目标：完成"看得见的改造" + 至少 1 个自研特色功能，形成原创亮点。

  • 至少走通 1 次 MR 合并流程。

AI 提示词 → P5

阶段 5 · 编译构建与持续集成W5 · 11-23~11-29A 主导

目标：配置 Maven 构建任务并成功产出发布包，开启代码变更自动构建（11%）。

具体步骤

  1. 在 DevCloud「编译构建」创建构建任务，选择 Maven 构建、Java 环境，构建命令 mvn clean package -Dmaven.test.skip=true -Pdev。
  2. 配置产物路径（如 blog-web/target/*.jar、blog-admin/target/*.jar），执行构建，直到构建成功并生成发布包。
  3. 开启「持续集成」：设置代码合并/推送后自动触发构建。
  4. 验证：推一次代码，观察构建任务自动执行。
  5. 用提示词 P6 解决构建报错（依赖下载失败、JDK 版本等）。

验收标准

  • 构建任务执行成功，产出发布包（截图）。
  • 代码变更后构建自动触发（截图）。

交付物：构建配置 + 发布包 + 自动触发记录。

AI 提示词 → P6

阶段 6 · 部署上云W6 · 11-30~12-06A 主导，B 配合

目标：把博客部署到华为 ECS，公网可访问（14%，占比最高，务必做好）。

具体步骤

  1. 购买/申请华为 ECS（学生优惠或老师提供），记下公网 IP。
  2. 在 DevCloud 对主机授信（主机配置拿分点）。
  3. ECS 上装 JDK + MySQL + Redis（或用 OneBlog 的 Docker Compose 一键部署，更快）。
  4. 在 DevCloud 创建部署任务：上传发布包 → 解压 → 执行启动脚本（或 docker 部署）。
  5. 执行部署，浏览器访问 http://公网IP:端口，确认首页打开。
  6. 配置安全组开放端口；有条件可绑定域名/HTTPS（加分）。
  7. 用提示词 P7 解决部署问题（端口不通、JDK 版本、内存不足）。

验收标准

  • 公网能访问博客首页，登录/发文/评论可用。
  • 部署任务执行成功（截图）。

交付物：可访问的线上博客 + 部署配置截图。

AI 提示词 → P7

阶段 7 · 分支合并与持续交付W7 · 12-07~12-13A 主导

目标：规范分支合并流程（难点），并搭建完整持续交付流水线（10%）。

具体步骤

  1. 给 Master 分支设置保护规则（禁止直接推送，只能通过 MR 合入）。

  4. 执行流水线，确认三步全绿，实现"一次提交、自动上线"。

验收标准

  • Master 有保护，一次完整 MR 流程走通（截图）。
  • 流水线跑通检查→构建→部署（截图）。

交付物：分支保护配置 + MR 记录 + 流水线记录。

AI 提示词 → P10

6AI 协作提示词手册

和 AI 高效协作的核心不是"问得多"，而是给足上下文 + 说清要什么。下面是一个万能公式和 10 个可直接复制的阶段提示词。

6.1 万能提示词公式（先记住这个）

角色：你现在是一名【资深 Java 工程师 / 产品经理 / DevOps 工程师 / 测试工程师】
背景：我在做【软件工程大作业：个人博客】，用【SpringBoot 2.x + MySQL + Redis】，目前进展到【哪个阶段】
任务：请你【具体要做的一件事】
要求：①…②…③…（版本、风格、边界、不要什么）
输出格式：【表格 / Markdown / 完整代码 / 分步骤 / 100字以内】
5 条高效原则
  • 一次只问一件事：让 AI 干"登录功能"就别同时塞"部署+测试"。
  • 报错必带原文：贴完整报错/日志，别只说"报错了"。
  • 指定版本：说"SpringBoot 2.3.5 / JDK 8"，否则 AI 容易用过时或过新的写法。
  • 追问式迭代：先要框架 → 再细化 → 再让 AI"检查自己写的有没有问题"。
  • 要对比不要单一答案：问"给我两种方案并对比优劣"，比"给我一个方案"质量高得多。

P1 · 需求分析

你是产品经理。帮我把"个人博客"拆成用户故事(Story)。
格式：每条用"作为[角色]，我想要[功能]，以便[价值]"，并标注优先级(P0/P1/P2)和验收标准。
功能范围至少覆盖：用户登录、发表/编辑/删除文章、文章评论、文章列表/分类/标签、后台管理。
再加 1~2 个有亮点的特色功能建议。用 Markdown 表格输出。

P2 · 架构设计

你是 Java 架构师。设计个人博客的系统架构，技术栈 SpringBoot 2.3.5 + MySQL + Redis + Shiro + Freemarker。
输出：①分层架构说明(文字即可)；②数据库 ER 图(用 Mermaid 或文字描述)；③核心表建表 SQL。
表至少包含用户、文章、分类、标签、评论。要求可直接用于 MySQL 5.6+。

P3 · 编码/二次开发定位

我在二次开发开源博客 OneBlog(SpringBoot+Freemarker)。现在想把【站点名称/Logo/首页配色】改成【xxx】。
请先说明大致要改哪些文件/配置，再给出关键修改片段。不要一次性重写整个项目，先给改动点清单。

P4 · 报错排障

我的代码报错如下(贴完整报错/日志)：
【粘贴报错信息】
技术栈 SpringBoot 2.3.5 + JDK 8 + Maven。请分析根因，给出修复方案，并说明为什么。先给原因，再给代码。

P5 · 特色功能开发

你是前端工程师。在 SpringBoot+Freemarker+Bootstrap3 的博客里新增"标签云/归档页/暗黑模式切换"功能。
要求：①给出前后端完整改动；②不破坏现有布局；③代码可直接粘贴运行。先给思路，再给完整代码。

P6 · 构建排障

我在华为云 DevCloud 配 Maven 构建(SpringBoot 多模块工程)，报错/卡在【xxx】。
构建命令是 mvn clean package -Dmaven.test.skip=true -Pdev。
请分析原因(依赖下载/JDK版本/多模块顺序)，给出在 DevCloud 上正确的构建配置步骤。

P7 · 部署排障

我要把 SpringBoot jar 部署到华为云 ECS(CentOS/Ubuntu)。
给出从上传到启动的完整步骤：安装 JDK、初始化 MySQL、上传 jar、nohup 后台启动、开机自启、防火墙/安全组放行端口。
遇到【具体报错】时该怎么排查。分步骤输出，标注每一步的目的。

P8 · 分支与流水线

你是 DevOps 工程师。解释并指导：①Git 功能分支 + MR(合并请求) 的标准流程和命令；②如何在 DevCloud 配一条"代码检查→编译构建→部署"的持续交付流水线。
面向零基础，每一步说清楚"在哪个页面点什么"。用分步骤输出。

P9 · 测试用例

你是测试工程师。为个人博客(登录/发文/编辑/删除/评论/后台)设计测试用例。
用表格输出：用例编号/前置条件/操作步骤/预期结果。覆盖正常和边界(空输入、超长、重复提交、未登录访问)。

P10 · 总结报告

帮我写软件工程大作业"个人博客开发过程总结"，要求有思考深度、结合敏捷与 DevOps 方法论。
框架：①项目概述；②开发过程(需求→设计→编码→构建→部署→交付，逐步写)；③DevOps 平台使用体会；④踩坑与解决；⑤思考与建议(如果重来怎么做)。
风格：正式、条理清晰、适合作为课程报告，2000~3000 字。先给大纲，我确认后再逐节展开。

7.1 术语表

术语含义
Story（用户故事）从用户视角描述的一个小功能，如"作为用户，我想登录"
迭代（Sprint）一个固定周期（1~2 周）内交付一批 Story 的开发节奏
CI / 持续集成代码提交后自动构建、自动检查
CD / 持续交付构建产物自动部署到服务器
MR / 合并请求把功能分支的代码请求合入主分支并接受审查
ECS华为云弹性云服务器
DevCloud华为云一站式软件开发平台
RBAC基于角色的权限控制

7.3 最容易踩的 5 个坑

  1. 在 Master 上直接改代码——作业明确要求功能分支 + MR，且这是 5% 的考点。
  2. 只顾写功能，忘了 DevCloud 截图——60% 的分数靠"痕迹"，每步做完立刻截图。
  3. JDK 版本不匹配——OneBlog 用 JDK 8，别用 JDK 11/17 直接跑。
  4. 构建/部署报错直接抄 AI 不改环境——先看是不是依赖源、内存、端口问题。
  5. 总结报告堆截图不写思考——15% 的"思考建议"要真反思，不是流水账。
