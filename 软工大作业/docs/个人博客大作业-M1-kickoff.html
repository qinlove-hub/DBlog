3 开始实现前的接口检查单

3.1 用户故事契约

  • 格式固定为「作为 [角色]，我想要 [功能]，以便 [价值]」；每条附优先级（P0 / P1 / P2）与可验证的验收标准。
  • 数量底线：Story ≥ 10 条，且必须覆盖作业点名的三大功能（登录、发表文章、评论）与基本博客要素（列表、分类、标签、后台管理）。
  • 特色功能作为独立 Story（P2），与二次开发改造点一一对应，避免写成"顺手加个功能"的模糊描述。

3.2 Story 字段契约

  • 每个 Story 必须填齐：描述、优先级、开始日期、结束日期、预计工时、重要程度，缺一项即视为工作项未完成（评分点「工作项设置」）。
  • 优先级定义：P0 = 作业明确点名的核心功能（登录/发文/评论）；P1 = 博客基础要素（列表/分类/标签/后台）；P2 = 特色功能与改造。
  • 日期落在 M3~M4 的迭代周期内，不能把需求写成"无期限"。

3.3 DevCloud 配置规范

  • 项目模式选 Scrum；思维导图层级 ≥ 3 层（Epic → Feature → Story）。
  • 迭代 ≥ 2 个，周期明确（建议迭代1 = 核心功能，迭代2 = 改造与特色功能）。
  • 每完成一步立即截图，命名 M1-规划-思维导图.png、M1-工作项-列表.png、M1-迭代-看板.png 之类，便于报告引用。

3.4 技术基线（M1 只确认、不实施）

  • 二次开发对象 OneBlog：SpringBoot 2.3.5、JDK 8、MySQL 5.6+、Redis、Apache Shiro、Freemarker、Bootstrap 3。
  • 特色功能候选：暗黑模式切换、标签云、归档页、文章点赞、Markdown 目录（M1 只需在需求里定 1~2 个）。
  • 上述版本约束写入需求文档的「技术选型」小节，供 M2/M3 直接执行，避免后续 JDK 版本不匹配的返工。

4 交给成员的可复制提示词

给吴凯阳：需求分析与用户故事

请按《软件工程-敏捷DevOps开发方法》大作业 V1.1 的要求，为"个人博客"项目撰写需求文档与用户故事清单。本提示用于交接，先核对实际分工（需求文档归你，DevCloud 平台配置归秦庆泽），不把任务表当作秦庆泽已接受。先读大作业文档 1.2 大作业要求、1.4 评分标准、2.1 项目管理三小节，以及《个人博客开发手册》的"阶段划分"与"各阶段操作"两节。

本轮范围是 M1.1：产出可评审的需求文档，内容至少覆盖用户登录、发表/编辑/删除文章、文章评论、文章列表/分类/标签、后台管理，以及 1~2 个特色功能（暗黑模式/标签云/归档页/点赞任选）。用户故事固定用"作为[角色]，我想要[功能]，以便[价值]"格式，每条标注优先级(P0/P1/P2)和可验证的验收标准；P0=作业点名功能(登录/发文/评论)，P1=基础要素，P2=特色功能与改造。Story 总数不少于 10 条。另加一节"技术选型"，写清二次开发对象 OneBlog(SpringBoot 2.3.5 + JDK 8 + MySQL + Redis + Shiro + Freemarker)与特色功能的技术路线。

边界：本轮只写需求文档，不写业务代码、不建数据库、不在 DevCloud 配置项目、不部署。输出 Markdown 格式，先给大纲(章节结构)让我和秦庆泽确认，再逐节展开；正文每条 Story 用表格列出，验收标准要具体到"输入什么、看到什么"。写完后自查：三大功能是否全覆盖、Story 是否 ≥10 条、每条是否带优先级和验收标准。文档存为 docs/requirements.md。

给秦庆泽：DevCloud 项目管理三环节

请按《软件工程-敏捷DevOps开发方法》大作业 V1.1 的 2.1 项目管理(2.1.1 规划 / 2.1.2 工作项 / 2.1.3 迭代)要求，在华为云 DevCloud 上完成个人博客项目的项目管理三环节。本提示用于交接，先核对实际分工(DevCloud 配置归你，需求文档归吴凯阳)，不把任务表当作吴凯阳已接受。先读大作业文档 1.3 软件开发平台、1.4 评分标准、2.1 项目管理，以及《个人博客开发手册》的"各阶段操作·阶段1"。

本轮范围是 M1.2~M1.5：① 新建 Scrum 项目"个人博客"；② 在"规划"用思维导图把需求拆成 Epic→Feature→Story 层级(≥3 层)，保存后确认 Story 自动生成到"工作项"；③ 在"工作项"逐条补全字段——描述、优先级(P0/P1/P2)、开始/结束日期、预计工时、重要程度；④ 创建迭代 1、迭代 2，按优先级从高到低排入 Story；⑤ 每步截图归档到 docs/evidence/M1/。

边界：本轮只做 DevCloud 项目管理的规划/工作项/迭代三个页面，不建代码仓库、不写代码、不建数据库、不配构建、不部署(那些是 M2~M6)。验收对应评分 15%(规划 5% + 工作项 5% + 迭代 5%)，但只有三个页面都真实填完并截图才算本轮完成；思维导图缺层级、字段缺项、迭代未排 Story 时，M1 保持"进行中"。操作时如遇平台界面与教程不符，以实际页面为准并记录差异。完成后更新阶段进度记录，不预填"已通过"。

3 证据留痕 三环节截图归档、可追溯、与报告引用一致 截图命名规范、存放 docs/evidence/M1/

每次记录：实际负责人、修改文件/页面、对应评分项、日期、截图位置、失败原因与限制。不预填验收通过，不编造尚不存在的菜单或按钮。

M1 整阶段退出需同时满足：

  1. 需求文档含 ≥10 条用户故事，每条带优先级(P0/P1/P2)与验收标准，三大功能（登录/发文/评论）全覆盖。

  3. 「工作项」字段（描述/优先级/开始结束日期/预计工时/重要程度）逐条填齐。
  4. ≥2 个迭代已创建，Story 按优先级从高到低排入。
  5. 规划/工作项/迭代三环节截图齐备并归档到 docs/evidence/M1/。
